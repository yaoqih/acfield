# 故障排查

先读取 `/api/health`、`/api/state` 中的事件和车端串口，再决定改配置。停车原因通常比“按钮没反应”更接近故障来源。

| 现象 | 优先检查 |
| --- | --- |
| 页面能打开，小车不能动 | 全局停止是否释放；是否显式解锁；控制 ID 是否一致 |
| 真实模式不能解锁 | 设备身份与绑定、心跳、定位有效、固件版本、故障锁存 |
| 一解锁就停车 | 定位跳变、车距/边界包络、心跳或动作到期 |
| 相机在线但定位失效 | 实际帧龄、标签遮挡、场地标定、来源声明和质量门限 |
| 运行几百毫秒后停止 | 是否在 TTL 期限内续发；策略/服务是否阻塞 |
| 第二个页面不能控制 | 同车控制权互斥；先在原控制源锁定或等待超时 |
| 日志不完整 | health 的 dropped/error、磁盘与目录权限 |
| 固件编译成功但电机不动 | motorsEnabled、每圈计数、故障锁存、方向与接线 |

## 故障与警告表 {#fault-codes}

以下对应当前固件 **0.2.3**。先区分 `/api/state` 中的字段：

| 字段 | 含义 |
| --- | --- |
| 车辆 `warning` | 设备警告；只显示提示，不停车、不锁定，不影响解锁、控制权或运动 |
| 车辆 `fault` | 设备锁存故障；立即停车并取消解锁，只接受停车指令。排除原因并重启车端后，重新绑定、显式解锁 |
| 车辆 `stop_reason` | 车端当前状态或最近停机原因；即使变为 `server_stop`，也不能据此认为 `fault` 已清除 |
| 车辆 `reason` | 主控的控制状态、等待原因或保护原因，通常是中文提示 |
| 顶层 `system_fault` | 控制/视觉后台任务异常，格式为任务名和异常类型；全车停止，排除原因后重启主控服务 |

| 代码 | 级别 | 触发条件（默认配置） | 排查与恢复 |
| --- | --- | --- | --- |
| `battery_sensor` | `warning` | INA219 读取失败、转换未就绪或电压超出 7–16 V；电压显示为未知 | 检查供电、I2C 线与地址 `0x42`；下一次有效读数自动清除，无需重启。异常读数中断欠压计时 |
| `battery_low` | `fault` | 有效电压连续低于 10.5 V 达 1 s | 测量电池与负载压降，充电或更换电池；电压恢复不会清除已锁存故障，需重启车端 |
| `motors_disabled` | `fault` | 编译配置 `motorsEnabled=false` | 确认标定后改为 `true`，重新编译烧录；仅网页解锁无效 |
| `encoder_calibration_required` | `fault` | 任一侧 `pulsesPerTurn` 不大于 0 | 测量并填写单相 RISING 每输出轴转计数，重新编译烧录 |
| `control_overrun` | `fault` | 控制周期无效、为 0 或超过 100 ms | 检查任务阻塞、互斥等待与控制任务负载；排除原因后重启车端 |
| `encoder_no_response_left` | `fault` | 左轮有非零目标，至少 800 ms 无编码脉冲，且累计目标行程达到 3 个脉冲距离 | 检查左轮堵转、接线、编码器供电和每圈计数；排除原因后重启车端 |
| `encoder_no_response_right` | `fault` | 右轮满足相同无响应条件 | 检查右轮堵转、接线、编码器供电和每圈计数；排除原因后重启车端 |
| `encoder_direction` | `fault` | 反馈持续约 200 ms 与目标反向，反馈绝对值大于 0.01 m/s 且目标与反馈乘积小于 −0.0001 | 架空核对 `motorSign`、`encoderSign` 与线序；当前代码不区分左右侧，结合串口两轮数据判断，修正后重启 |

版本差异：旧版 **0.2.1** 的 `battery_sensor` 是锁存故障。若页面仍显示“设备故障：battery_sensor”，需更新配套主控和固件并重启车端；刷新页面或释放全局停止无法清除旧固件的锁存。**0.2.3 已移除 `wheel_overspeed` 故障**，较旧固件中该代码表示实测轮速超过固件轮速上限的 3 倍；当前固件仍限制目标轮速。旧主控可能拒绝带新 `warning` 字段的遥测，即使值为 `null`，因此两端要一起升级。

## 停车、等待与恢复 {#control-states}

以下是状态或控制条件，不等同于设备锁存故障；先处理 `fault` 或 `system_fault`，再按提示恢复控制。

| 提示或 `stop_reason` | 含义与恢复 |
| --- | --- |
| `boot`、`server_stop` / 等待停车绑定确认 | 启动或收到停车；等主控与车端完成停车确认后显式解锁。固件在线但一直无法确认时，检查车端身份、主控地址及版本；0.2.2 已修复可变 JSON 缓冲区重复解析造成的指令拒收 |
| `link_lost` / 设备连接、重连 | Wi-Fi 状态变化或主控检测到重连；恢复通信、完成停车绑定后重新解锁，不会自动续驶 |
| `command_timeout` / 指令超时 | 非零运动指令未在 TTL 内续发（允许 100–500 ms）；恢复续发并重新解锁，重复序号不会续期 |
| `armed`、`idle`、`driving` | 正常状态：已解锁、零速保持解锁、运动中 |
| 设备离线 | 主控超过 1 s 没有收到有效遥测；检查电源、Wi-Fi、固件主控 IP、UDP 端口及协议兼容性 |
| 定位已过期 / 定位不可用 | 要求定位时，位姿超过 200 ms；检查标签、相机与标定，定位恢复后重新解锁 |
| 等待车端时间同步 / 等待浏览器与控制服务时间同步 | 两段校时分别检查车端到主控的 UDP、浏览器到主控的 WebSocket；校时就绪后才能使用网页运动控制 |
| 场地边界保护 / 车间距离保护 / 其他小车定位失效 | 检查各车位置、车体包络与预测路径，恢复满足条件后显式解锁。设置 `ROBOT_ALLOW_UNLOCALIZED_CONTROL=1` 时跳过定位、边界和车距检查 |
| 全局停止已锁定 | 释放全局停止后逐车解锁；释放操作不会清除设备故障或自动继续运动 |
| 另一页面正在控制 / 控制权已过期 | 控制权互斥，原控制源先锁定或释放；控制权 10 s 未续期会停车，之后重新解锁 |
| 视觉配置正在更新 / 视觉配置同步失败 | 等待同步完成或修复视觉服务连接与配置，再重新解锁 |

串口 `[status]` 可同时查看 `fault`、`warning`、左右目标/实测轮速、PWM 与编码计数。保存问题记录时同时附上这些值、固件版本和事件，避免只记录页面上的一句提示。

## 前端缺失 {#missing-frontend}

`./run.sh` 会在缺少产物时尝试安装并构建前端。若失败，检查 Node 版本与依赖安装；手动执行 `npm --prefix frontend ci` 和 `npm --prefix frontend run build`。已有旧构建时，源码改动后需要重新构建。

## 契约测试被跳过 {#skipped-contract-tests}

后端测试需要主机 C++ 编译器和 PlatformIO 安装的 ArduinoJson。先运行：

```bash
python3 -m pip install platformio==6.1.18
pio pkg install -d esp32_software/firmware -e general-driver
```

本地缺依赖时测试明确跳过；CI 设置 `ACFIELD_REQUIRE_FIRMWARE_CONTRACT=1`，依赖缺失必须报错，避免测试假绿。

## 端口占用 {#ports-already-in-use}

控制默认 HTTP 8000、设备 UDP 9999、视觉 HTTP 8765。检查旧进程是否仍在运行；不要为解决占用直接增加控制服务 worker。可以修改端口，但服务、固件与示例的地址必须一致。

## Linux 原生检测器退出崩溃 {#native-detector-crashes-on-linux-cleanup}

pupil-apriltags 1.0.4.post11 的上游清理顺序可能在 Linux 释放检测器时触发崩溃，参见 [上游修复讨论](https://github.com/pupil-labs/apriltags/pull/76)。本仓通过 `native_apriltag.py` 在释放标签族前先释放检测器，依赖版本暂时固定，并用独立子进程反复检测与销毁进行回归检查。更新原生依赖时应一起复核该兼容层。

## 提交有效的问题报告 {#report-a-useful-issue}

附平台提交、运行模式、操作系统、固件与硬件版本、最小复现步骤、相关事件与停车原因。说明哪些是实测、哪些是推测。移除凭据和私有数据后，使用 [Bug Report](https://github.com/yaoqih/acfield/issues/new/choose) 模板提交。
