# 故障排查

先读取 `/api/health`、`/api/state` 中的事件和车端串口，再决定改配置。停车原因通常比“按钮没反应”更接近故障来源。

| 现象 | 优先检查 |
| --- | --- |
| 页面能打开，小车不能动 | 全局停止是否释放；是否完成停车绑定；控制 ID 是否一致 |
| 真实模式无法开始控制 | 设备身份与绑定、心跳、定位有效、固件版本、故障锁存 |
| 一操作就停车 | 定位跳变、车距/边界包络、心跳或动作到期 |
| 相机在线但定位失效 | 实际帧龄、标签遮挡、场地标定、来源声明和质量门限 |
| 运行几百毫秒后停止 | 是否在 TTL 期限内续发；策略/服务是否阻塞 |
| 第二个页面不能控制 | 同车控制权互斥；先在原控制源锁定或等待超时 |
| 日志不完整 | health 的 dropped/error、磁盘与目录权限 |
| 固件编译成功但电机不动 | motorsEnabled、每圈计数、故障锁存、方向与接线 |

## 编码器线材排查

1. 将小车架空，确保双轮离地，在控制台打开「编码器排查」（也可访问 `/encoder`），选择小车并确认在线。
2. 诊断固件显示 PWM 输入，先设置较小占空比，直接点击「开始前进」或「开始后退」。运行中修改数值后点击「应用输出」即可调整，无需停车重启；超出上限的输入会提示错误，不会悄悄截断。双轮持续运行时轻晃线材或插头，比较左右计数和曲线；结束后点击「停车」。页面失焦或切到后台继续运行，单次最多 2 分钟；离开页面、控制连接断开或切车时停车锁定。PWM 设为 0 并应用只停转，保持解锁。普通固件显示目标速度，本页上限为 0.10 m/s 与车辆有效上限的较小值。
3. 曲线是遥测中的原始累计计数相对当前窗口内每段起点的变化，没有应用 `encoderSign`；左右计数的正负可能不同。它只反映遥测采样，不是每个脉冲的波形。数据中断后曲线断开并重新起算；模拟模式没有编码器数据。
4. 如果一侧计数停滞或突变，结合串口的轮速、PWM 和接线检查，不能单凭曲线认定故障。0.2.7 默认开环，编码器异常不改变 PWM；编码器无响应和方向故障停车也保持关闭。旧固件或重新启用闭环与保护的构建仍会锁存，排除原因后重启车端再直接操作。

诊断页通过 WebSocket 提交持续运行指令，由主控每 25 ms 续发有效期 500 ms 的车端命令，避免浏览器切后台后的定时器降频打断运动。不依赖浏览器或车端校时，校时状态变化不会单独触发停车。普通固件使用网页续发，由主控按车端校时状态选择排程或即时发送。点击停车、退出页面或 WebSocket 断开时清除主控续发；离线、实际设备故障、全局停止仍会停止并清除续发，恢复后不会自动重启。页面记录具体停车原因，`server_stop` 只表示车端收到了停车指令。

2026-11-12 日志中 15:50:51、15:51:00、15:51:15 的三次停车均为车端 `command_timeout`。期间主控仍约每 25 ms 发包，但有效遥测接收出现约 600–770 ms 空档，确认序号停止前进；旧固件要求运动指令回显 200 ms 内的遥测，因此持续发包也可能被拒收并最终超时。`0.2.4-encoder-diagnostic` 将运动回显窗口放宽为 1500 ms，绑定和解锁仍为 200 ms；新增 `motion_echo_rejections` 开机累计计数，页面与日志可查看，判断是否仍因回显过期而拒收。有效遥测空档不一定是网络丢包，也可能是下述主控校验丢包；旧日志未记录每次拒收原因，也无法还原旧版通用「控制源已释放」究竟由哪个页面事件触发。

随后 16:05–16:09 日志出现 8 次 1046–1129 ms 的有效遥测空档，车端启动 ID 未变、无故障且 `motion_echo_rejections=0`。主控旧 1 s 心跳期限先触发「设备离线」停车，再在恢复遥测时覆盖为通用「设备连接 / 重连」。当前已将普通与诊断固件的心跳及遥测重连判定统一放宽为 3 s；真正重启、通信地址变化和遥测超时恢复分别记录具体原因。设备本地运动 TTL 仍为 500 ms；放宽主控心跳只容忍遥测返回的短暂空档，不能保证双向网络中断时继续运行。日志另有 16:06:40、16:08:13 两次旧页面主动触发 30 s 停车，现改为主控 120 s 截止。

深入检查发现主控遥测校验曾把 `wheel_left/right` 限定在 ±3 m/s、`measured_v` 限定在 ±3 m/s、`measured_omega` 限定在 ±30 rad/s。编码器干扰或计数标定偏差会使这些估算值越界，导致整包（包括心跳、ACK、原始计数）被静默丢弃；电机被 1 s 心跳停车后测速回零，遥测又被接受，形成约 1 s 的假离线。16:08:19.723–16:08:20.771 左计数变化 2483，按当前参数约合 4.22 m/s；16:09:13.122–16:09:14.177 变化 33524，约合 56.6 m/s。记录中已接受的轮速最大值恰为量化后的 2.848 m/s，超过校验范围的报文不在旧日志中。这些证据与校验丢包高度吻合，旧日志无法逐包排除叠加的网络丢包。现保留所有有限的原始测速值，NaN/Infinity 仍拒收，异常测速不再抹掉心跳和诊断曲线。此修复只需更新并重启主控，无需再次烧录已在运行的 `0.2.4-encoder-diagnostic`。

主控 `/api/health` 新增 `udp_received`、`udp_rejected`、`udp_rejections`（拒收原因计数），运行日志新增 `udp_rejected`，包含来源地址、拒收原因和校验字段。若再次出现空档，先看拒收计数是否增长，再检查 Wi-Fi；单凭已接受遥测的序号跳变不能断定网络丢包。16:10:53 新运行中存在 581/698 ms 空档，恢复时仍为 `armed/driving`，最终在 16:13:16 按 120 s 截止停车；这是较宽心跳与主控续发已生效的实测，发生于此次测速校验修复之前。

需要在编码器断线期间继续转轮时，CAR-01 可烧录专用诊断固件：

```sh
cd esp32_software/firmware
pio run -e encoder-diagnostic -t upload
pio device monitor
```

`0.2.4-encoder-diagnostic` 禁用编码器无响应和方向保护，以开环方式驱动双轮，PWM 开放完整 0–255。主控诊断 PWM 路径不使用普通 m/s 配置限速；页面显示主控指令 PWM 和左右轮编码器估算速度。PWM 不代表 m/s，编码器接触不良时测速也不可信。旧 `0.2.3-encoder-diagnostic` 固件内部仍限幅 35/255，必须重新烧录才能使用完整输出与 1500 ms 回显窗口；页面识别旧固件时显示真实上限和升级提示。

主控按明确固件版本识别 `v=PWM/350` 映射，协议内 `v` 是诊断传输值，不是物理速度。若修改前馈或诊断上限，应同步更新版本和主控映射。诊断设置对该车收到的所有运动指令生效，只用于架空排查。停车、指令超时、欠压等其他保护仍生效。重新烧录会重启车端并清除原先锁存的编码器故障。排查结束后，从仓库根目录执行 `pio run -d esp32_software/firmware -e general-driver -t upload` 切回 **0.2.8** 普通固件；当前默认开环，仍关闭编码器故障停车。

普通固件每 10 ms 更新一次控制，使用最近 5 周期（约 50 ms）的脉冲总数/实际时长估速，原始累计计数不滤波。摇杆发送频率保持 **40 Hz（25 ms）**，PWM 输出仍可达到 255。0.2.7 默认 `motorClosedLoop=false`，编码器仅用于显示与记录，不再参与 PI 或改变 PWM；`encoderGuardsEnabled=false` 继续关闭编码器故障停车。启动串口应显示 `Motor control: open_loop`。

### 前进断续或抖动

0.2.6 日志曾在约 0.17 m/s 的直行目标下记录约 5.98 m/s 的左轮估算反馈。PI 比例项会因此将正向输出压到 0，反馈回落后再提高输出，可能形成反复加速、滑行。关闭编码器故障停车不能阻止这种调节。0.2.7 用开环隔离反馈干扰；若输出 PWM 稳定而实车仍抖动，继续检查低占空比起转、供电压降、驱动和机械阻力，不能只归因于编码器。

## 速度设置与实测

控制台配置中的「最大线速度」是目标上限。摇杆目标按推杆幅度与有效上限计算，有效上限取主控配置与固件限制的较小值；把主控设置为 1 m/s 不等于车会跑到 1 m/s。普通固件当前目标上限为 0.89 m/s，主控新建车辆默认 0.50 m/s。0.2.7 开环按左右目标轮速乘 350 输出 PWM，例如直行目标 0.10、0.20、0.50 分别对应约 35、70、175；任一轮超过 255 时两轮等比例缩放，保留转向比例。页面单位保留 m/s，但开环实际速度随电量、负载和电机差异变化，不做恒速调节。

普通固件的轮速估算为 `每秒脉冲数 × π × 轮径 / 每圈脉冲数`。当前轮径为 0.034 m，每圈计数 60 来自减速比换算，尚需实测：手动转动每侧车轮 10 整圈，分别用原始计数差绝对值除以 10，校正 `pulsesPerTurn`，并确认前进反馈为正。编码器接触不良时，即使页面显示 1 m/s 也不能证明真实车速。线路稳定、轮径和计数校准、PI 整定后，设置 `motorClosedLoop=true` 恢复闭环，并用实测行驶距离/时间或经过标定的视觉速度交叉验证。编码器故障停车需另设 `encoderGuardsEnabled=true`；修改后重新编译烧录。

## 左右转反向与自动控制

0.2.8 保持正角速度为左转、右轮更快的约定，将当前车体的逻辑左/右轮映射到物理 B/A 通道；电机输出与编码器反馈使用同一个 `wheelChannels={1,0}`，避免只改摇杆符号导致反馈左右错配。前后方向沿用当前 `motorSign` / `encoderSign`。不同接线车辆应按实际安装调整该映射。

控制台、手机页和编码器页已移除手动解锁按钮。首次新输入自动完成控制握手；停车、超时或重连后，可直接再次推杆或点击运行。握手期间松开、停车或超出原始指令有效期会清除待执行动作，重连不会恢复旧运动。主控曾记录 1058 ms 遥测间隔，旧 1 s 阈值会触发重绑定；当前统一为 3 s，运动 TTL 和摇杆 40 Hz 保持原值。

## 故障与警告表 {#fault-codes}

以下对应当前普通固件 **0.2.8**（默认开环）。先区分 `/api/state` 中的字段：

| 字段 | 含义 |
| --- | --- |
| 车辆 `warning` | 设备警告；只显示提示，不停车、不锁定，不影响解锁、控制权或运动 |
| 车辆 `fault` | 设备锁存故障；立即停车并取消解锁，只接受停车指令。排除原因并重启车端后，完成绑定后直接重新操作 |
| 车辆 `stop_reason` | 车端当前状态或最近停机原因；即使变为 `server_stop`，也不能据此认为 `fault` 已清除 |
| 车辆 `reason` | 主控的控制状态、等待原因或保护原因，通常是中文提示 |
| 车辆 `last_stop_reason` | 主控最近一次停车原因；保留在停车绑定完成后，用于区分用户停车、切车、通信超时等情况 |
| 车辆 `motion_echo_rejections` | 新固件因运动指令回显过期/未知而拒收的开机累计次数；旧固件为 `null` |
| 顶层 `system_fault` | 控制/视觉后台任务异常，格式为任务名和异常类型；全车停止，排除原因后重启主控服务 |

| 代码 | 级别 | 触发条件（默认配置） | 排查与恢复 |
| --- | --- | --- | --- |
| `battery_sensor` | `warning` | INA219 读取失败、转换未就绪或电压超出 7–16 V；电压显示为未知 | 检查供电、I2C 线与地址 `0x42`；下一次有效读数自动清除，无需重启。异常读数中断欠压计时 |
| `battery_low` | `fault` | 有效电压连续低于 10.5 V 达 1 s | 测量电池与负载压降，充电或更换电池；电压恢复不会清除已锁存故障，需重启车端 |
| `motors_disabled` | `fault` | 编译配置 `motorsEnabled=false` | 确认标定后改为 `true`，重新编译烧录；仅网页解锁无效 |
| `encoder_calibration_required` | `fault` | 任一侧 `pulsesPerTurn` 不大于 0 | 测量并填写单相 RISING 每输出轴转计数，重新编译烧录 |
| `control_overrun` | `fault` | 控制周期无效、为 0 或超过 100 ms | 检查任务阻塞、互斥等待与控制任务负载；排除原因后重启车端 |
| `encoder_no_response_left` | 默认关闭 | 仅 `motorClosedLoop=true` 且 `encoderGuardsEnabled=true`：左轮有非零目标，至少 1500 ms 无原始编码脉冲，且累计目标行程达到 6 个脉冲距离；收到脉冲即重置 | 旧固件或启用闭环与保护时，检查左轮堵转、接线、编码器供电和每圈计数；排除原因后重启车端 |
| `encoder_no_response_right` | 默认关闭 | 仅启用闭环与保护时：右轮满足相同无响应条件 | 检查右轮堵转、接线、编码器供电和每圈计数；旧锁存需重启清除 |
| `encoder_direction` | 默认关闭 | 仅启用闭环与保护时：平滑反馈连续至少 1000 ms 与目标反向，反馈绝对值大于 0.05 m/s、目标与反馈乘积小于 −0.0001，且累计反向反馈行程达到 6 个脉冲距离 | 架空核对 `motorSign`、`encoderSign` 与线序；结合串口两轮数据判断，旧锁存需重启清除 |

版本差异：旧版 **0.2.1** 的 `battery_sensor` 是锁存故障。若页面仍显示“设备故障：battery_sensor”，需更新配套主控和固件并重启车端；刷新页面或释放全局停止无法清除旧固件的锁存。**0.2.3 已移除 `wheel_overspeed` 故障**，较旧固件中该代码表示实测轮速超过固件轮速上限的 3 倍；当前固件仍限制目标轮速。旧主控可能拒绝带新 `warning` 字段的遥测，即使值为 `null`，因此两端要一起升级。

## 停车、等待与恢复 {#control-states}

以下是状态或控制条件，不等同于设备锁存故障；先处理 `fault` 或 `system_fault`，再按提示恢复控制。

| 提示或 `stop_reason` | 含义与恢复 |
| --- | --- |
| `boot`、`server_stop` / 等待停车绑定确认 | 启动或收到停车；等主控与车端完成停车确认后直接重新操作。固件在线但一直无法确认时，检查车端身份、主控地址及版本；0.2.2 已修复可变 JSON 缓冲区重复解析造成的指令拒收 |
| `link_lost` / 设备连接、重连 | Wi-Fi 状态变化或主控检测到重连；恢复通信、完成停车绑定后直接重新操作，不会自动续驶 |
| `command_timeout` / 指令超时 | 车端未在 TTL 内接受新的非零运动指令（允许 100–500 ms）；也可能持续发包却因遥测回显过期而拒收；恢复续发后自动准备控制，重复序号不会续期 |
| `armed`、`idle`、`driving` | 正常状态：已解锁、零速保持解锁、运动中 |
| 设备离线 | 普通与诊断固件超过 3 s 没有收到有效遥测；先看 health 的 UDP 拒收计数及日志字段，再检查电源、Wi-Fi、主控 IP 和端口 |
| 定位已过期 / 定位不可用 | 要求定位时，位姿超过 200 ms；检查标签、相机与标定，定位恢复后直接重新操作 |
| 时间同步未就绪 | 网页仍可控制，主控在车端未同步时即时发送。若长期未同步，分别检查车端到主控的 UDP 和浏览器到主控的 WebSocket；在线遥测只能证明车端到主控方向可达 |
| 场地边界保护 / 车间距离保护 / 其他小车定位失效 | 检查各车位置、车体包络与预测路径，恢复满足条件后直接重新操作。设置 `ROBOT_ALLOW_UNLOCALIZED_CONTROL=1` 时跳过定位、边界和车距检查 |
| 全局停止已锁定 | 释放全局停止后可直接操作；释放操作不会清除设备故障或自动继续运动 |
| 另一页面正在控制 / 控制权已过期 | 控制权互斥，原控制源先锁定或释放；普通控制权 10 s 未续期会停车，之后直接重新操作；持续诊断由主控续期，停止时清除 |
| 视觉配置正在更新 / 视觉配置同步失败 | 等待同步完成或修复视觉服务连接与配置，再直接操作 |

串口 `[status]` 可同时查看 `fault`、`warning`、左右目标/实测轮速、PWM 与编码计数。保存问题记录时同时附上这些值、固件版本和事件，避免只记录页面上的一句提示。

## 前端缺失 {#missing-frontend}

`./run.sh` 会在缺少产物时尝试安装并构建前端。若失败，检查 Node 版本与依赖安装；手动执行 `npm --prefix frontend ci` 和 `npm --prefix frontend run build`。已有旧构建时，源码改动后需要重新构建。

## 端口占用 {#ports-already-in-use}

控制默认 HTTP 8000、设备 UDP 9999、视觉 HTTP 8765。检查旧进程是否仍在运行；不要为解决占用直接增加控制服务 worker。可以修改端口，但服务、固件与示例的地址必须一致。

## Linux 原生检测器退出崩溃 {#native-detector-crashes-on-linux-cleanup}

pupil-apriltags 1.0.4.post11 的上游清理顺序可能在 Linux 释放检测器时触发崩溃，参见 [上游修复讨论](https://github.com/pupil-labs/apriltags/pull/76)。本仓通过 `native_apriltag.py` 在释放标签族前先释放检测器，依赖版本暂时固定，并用独立子进程反复检测与销毁进行回归检查。更新原生依赖时应一起复核该兼容层。
