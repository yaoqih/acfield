# 关键设计决策

这里记录当前选择、付出的代价，以及什么证据会促使我们改变选择。它不是永久技术路线。

## D01 · 一个主仓维护完整平台 {#d01-one-repository-for-the-complete-platform}

**选择：** 控制台、服务端、定位、固件、参考硬件与文档放在同一仓库。论文算法与训练实验独立，并固定依赖平台版本。

**原因：** 当前设备协议需要跨端联调，契约测试直接编译真实固件解析器。一次提交可以同时修改两端，用户也只需找到一套版本匹配的源代码。

**代价与调整条件：** 仓库包含多种工具链，完整 CI 成本较高。若某模块出现独立用户、独立维护者和稳定发布节奏，再考虑拆分；先明确版本兼容与集成测试如何继续承担。

## D02 · 固定相机提供公共定位 {#d02-a-fixed-camera-provides-shared-localization}

**选择：** 一台相机与 AprilTag 建立共享世界坐标，车端不承担 SLAM。

**原因：** 小规模室内低速实验更容易获得统一坐标，并把研究资源投入协作决策。

**代价与调整条件：** 相机是共同依赖，遮挡、反光和远端像素不足会限制场地。若目标转向车载感知、分布式定位或视线外运行，应更换或增加定位来源，并明确融合及误差模型。

## D03 · HTTP 接入策略，UDP 连接设备 {#d03-http-for-policies-udp-for-devices}

**选择：** 算法通过可检查的 HTTP 状态/联合动作接口接入，主控与 ESP32 使用小型 JSON UDP 协议。

**原因：** 参考规模消息量较小，联调门槛低，接口容易从不同语言调用。会话、序号、遥测回显和 TTL 负责处理常见乱序与陈旧指令。

**代价与调整条件：** HTTP 不是硬实时，UDP 不保证送达，也没有身份认证。需要更高频、精确同步、ROS 生态接入或网络隔离时，应根据测量结果增加适配或更换传输，保持失效行为可验证。

## D04 · 车端独立检查运动期限 {#d04-devices-check-motion-expiry-independently}

**选择：** 车端 50 Hz 运动任务检查 TTL 并执行轮速控制，网络与 I²C 操作在另一任务执行。

**原因：** 主控、网络或策略停止更新时，车辆需要依靠本地状态收敛到停车。

**代价与调整条件：** ESP32 调度、锁竞争和硬件行为仍需测量，软件看门狗也不等于确定的物理停止时间。若周期或停止距离达不到实验要求，应先测任务延迟和电机动态，再决定控制器升级。

## D05 · 演示先解决接入，仿真按需求建设 {#d05-use-the-demo-for-integration-build-simulation-to-need}

**选择：** 提供一个轻量运动学 demo，首先验证界面、接口和停车链路。

**原因：** 无设备用户也能理解系统，维护者无需运行大型仿真软件即可排查多数接口问题。

**代价与调整条件：** 当前模型没有固定步长研究接口、奖励、完整任务、摩擦和真实链路扰动。训练与性能排名需要独立验证的仿真和实验协议，不能直接沿用演示模式得出迁移结论。

## D06 · 保护动作要被看见 {#d06-make-protective-actions-visible}

**选择：** 保护层在主控检查边界、车距、定位和设备状态，记录动作限幅及拒绝原因。

**原因：** 保护机制让初次联调的失败模式更可控，同时可为解释实验提供证据。

**代价与调整条件：** 保护改变策略行为，且可能使用策略本身不可见的全局信息。研究应报告干预情况。若干预成为主要运行方式，应检查实验间距、模型、误差与策略适配，再调整阈值。
